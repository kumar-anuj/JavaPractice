1.5 Single-machine software (B)

  • Single-process app: all logic, state, storage in one process. Simple, fast, no network. Limits: one machine's CPU/RAM/disk; one crash = total outage; single user.
  • Batch processing: run job over bounded input (payroll). High throughput, no interactivity → interactive/time-sharing.
  • Mainframe & time-sharing: centralized compute, dumb terminals. Strong reliability, expensive, vendor lock-in → PC / client-server (reaction to cost).
  • Desktop apps: local compute, local files. Data siloed, no sharing → client-server (reaction to business requirements: shared data).

★ Why foundations shape design (summary)

  1. Disk vs RAM vs network latency ratios decide where data lives (cache, replicate, shard).
  2. Sequential I/O superiority → logs, LSM, append-only everything.
  3. Multicore → concurrency control → every shared-state bug class.
  4. Clocks unreliable → logical time, fencing tokens (Part 6).
  5. Crash consistency (journaling) → WAL/consensus logs across the stack.

2.6 Fallacies of distributed computing (Deutsch/Gosling)

The network is reliable · latency is zero · bandwidth is infinite · the network is secure · topology doesn't change · there is one administrator · transport cost is zero · the network is homogeneous.

★ Example – What happens on GET https://shop.com/

Client -> DNS (cache -> resolver -> authoritative; maybe GeoDNS)
       -> TCP/QUIC handshake -> TLS handshake (SNI)
       -> Anycast edge / CDN (cache hit? return)
       -> L4 LB -> L7 LB / API gateway (auth, rate limit)
       -> Service -> cache -> DB
       <- response (compressed, cacheable headers)

Each hop adds latency, a failure mode, a timeout, and a security boundary.

4.2 Modeling

  • ER modeling: entities, relationships, cardinality.
  • Normalization (1NF–BCNF): removes redundancy/update anomalies. Denormalization: duplicate for read speed, at the cost of write complexity/inconsistency.
  • Keys: primary (identity; choose monotonic vs random: UUIDv4 fragments B-tree, UUIDv7/ULID/snowflake are time-ordered), foreign (integrity; costly across shards).
  • Stored procedures: logic near data (fast, hard to version/test). Materialized views: precomputed query results (refresh cost/staleness).
  • Schema evolution & migrations: expand-and-contract; backward/forward compatibility; online DDL tools.
  • Polyglot persistence: right store per workload; cost is operational variety and cross-store consistency (use CDC/outbox).

4.4 Transactions & concurrency

  • ACID: Atomicity, Consistency (app invariants), Isolation, Durability. BASE: Basically Available, Soft state, Eventually consistent — reaction to scale/availability.
  • Isolation levels: Read Uncommitted → Read Committed → Repeatable Read → Snapshot → Serializable. Anomalies: dirty read, non-repeatable read, phantom, lost update, write skew.
  • Serializability (transactions behave as serial order) vs linearizability (single-object real-time recency) — different guarantees; strict serializability = both.
  • 2PL (pessimistic): shared/exclusive locks until commit; deadlocks → detection/timeouts. OCC (optimistic): validate at commit; retries under contention. MVCC: versions per row, readers don't block writers (Postgres, Oracle, InnoDB). SSI: serializable snapshot isolation.
  • Deadlocks: lock ordering, short txns, timeouts.

4.7 Consistency models & theory

  • CAP: during a Partition choose C (reject) or A (serve possibly stale). It's not "pick 2 of 3 always".
  • PACELC: if Partition → A vs C; Else → Latency vs Consistency (Dynamo: PA/EL; Spanner: PC/EC).
  • Spectrum (strong→weak): strict serializable → linearizable → sequential → causal → read-your-writes / monotonic reads / monotonic writes / session → eventual.
  • Consensus: Paxos/Raft/ZAB to agree on a log → linearizable replicated state machines.
  • Distributed transactions: 2PC (blocking on coordinator failure), 3PC (non-blocking in theory, impractical), Saga (compensations, eventual), TCC (try-confirm-cancel), Percolator/Spanner (timestamps + consensus).
  • Outbox: write event in same local txn as state; relay publishes (solves dual-write). Inbox: consumer stores processed message ids (dedup). Idempotency: same request repeated has same effect (idempotency keys, upserts, version checks).

Formulas

  • Little's Law: L = λ · W (concurrent requests = arrival rate × latency).
  • Throughput per instance ≈ cores / avg CPU time per request.
  • Amdahl: speedup = 1 / ((1-p) + p/n); Universal Scalability Law adds contention and coherency costs.
  • Tail at scale: if one call is slow 1% of time, a fan-out of 100 calls is slow 1-0.99^100 ≈ 63% of the time.
  • Utilization vs queueing: wait time grows ~ρ/(1-ρ); keep utilization ≲ 60–70% for latency-sensitive services.
  • Pool size ≈ QPS × avg DB time (s) (+ headroom).

Part 14 – Deep Dive A: Foundations and Networking (with examples and diagrams)

14.1 Why the memory hierarchy drives every design

Idea: fast storage is small and expensive; big storage is slow. Systems keep hot data close.

 Speed/Cost  ^                         Capacity
   fastest   |  Registers      (bytes)
             |  L1/L2/L3       (KB-MB)
             |  RAM            (GB)
             |  SSD            (TB)
             |  HDD / Object   (PB)
   slowest   |  Network/Remote (unbounded)

Worked example – why Redis in front of Postgres helps: a Postgres indexed read costs ~1 ms (buffer-pool hit) up to ~10 ms (disk). A Redis read over the LAN costs ~0.3 ms. At 95% hit ratio: 0.95×0.3 + 0.05×10 = 0.785 ms vs 10 ms uncached – a 12× gain, and the DB sees 20× fewer queries.

Sequential vs random I/O example: an HDD does ~100 random IOPS (~0.4 MB/s with 4 KB reads) but ~150 MB/s sequential. This is why Kafka appends to a log, databases write a WAL first, and LSM trees batch writes into sorted files.

14.2 Processes, threads, locks – a runnable Java example

// Race condition and fix
class Counter {
    private int unsafe = 0;                       // not thread-safe
    private final java.util.concurrent.atomic.AtomicInteger safe =
        new java.util.concurrent.atomic.AtomicInteger();   // CAS-based

    void incUnsafe() { unsafe++; }                // read-modify-write: 3 steps, interleavable
    void incSafe()   { safe.incrementAndGet(); }  // atomic compare-and-swap loop
}
// Two threads each doing 1,000,000 incUnsafe() typically end < 2,000,000.

Thread A: read 5 ----------- write 6
Thread B:      read 5 -- write 6          <- lost update (should be 7)

Deadlock example: T1 locks A then B; T2 locks B then A.

T1: lock(A) ---- wait(B)
T2: lock(B) ---- wait(A)      => cycle => deadlock
Fix: always acquire locks in global order (A then B), or use tryLock(timeout).

Context-switch cost → design: 10,000 threads blocked on I/O waste memory (~1 MB stack each) and CPU switching. Response: event loops (Netty/Node), async I/O (epoll), Java virtual threads, or actors.

14.3 Filesystem journaling example

Without journal: write data block -> CRASH -> metadata not updated -> corrupted file
With journal:    1. write "intent" to journal  2. commit marker
                 3. apply to real location       4. clear journal
On reboot: replay committed entries, discard incomplete ones.

The same log-first idea appears in database WAL, Raft logs, and Kafka.

14.6 TCP essentials with examples

  • Handshake: SYN → SYN-ACK → ACK (1.5 RTT before data).
  • Flow control: receiver advertises window; if window = 0 the sender pauses (cousin of application backpressure).
  • Congestion control: slow start doubles the window each RTT until loss, then backs off (AIMD). Short flows never leave slow start → keep connections alive and pooled.
  • Head-of-line blocking: one lost packet stalls all later data on that TCP stream, even for unrelated HTTP/2 requests → QUIC gives independent streams.
HTTP/1.1 : [req1][resp1] [req2][resp2] ...             (serial per connection; 6 parallel conns)
HTTP/2   : req1,req2,req3 interleaved on 1 TCP conn     (TCP HOL on loss)
HTTP/3   : req1,req2,req3 as independent QUIC streams   (loss affects only one stream)

16.1 Indexes and storage engines

Without an index SELECT * FROM orders WHERE user_id=42 scans every row (O(n)). With a B+ tree index on user_id it is O(log n).

B+ tree (fan-out ~100-500):            Root:      [ 30 | 60 ]
 3-4 levels hold billions of rows      Internal:  [10|20] [40|50] [70|80]
 leaves are linked -> range scans      Leaves: [..]->[..]->[..]->[..]   (linked list; hold row pointers/rows)
  • Composite index (user_id, created_at) serves WHERE user_id=? ORDER BY created_at; leftmost-prefix rule: it does not help WHERE created_at=? alone.
  • Covering index includes all selected columns → no table lookup.
  • Cost: each index slows writes and uses space. Index selectivity matters (an index on a boolean is rarely useful).
  • Check plans: EXPLAIN ANALYZE SELECT ....

LSM tree write path

write -> WAL (durable) -> Memtable (sorted, in RAM)
          memtable full -> flush -> SSTable L0 -> compaction merges into L1, L2 ...
read  -> memtable -> bloom filter -> SSTables newest->oldest

Trade-off: writes sequential and fast; reads touch several files (bloom filters help); compaction causes write amplification and latency spikes.

Reads 1 path Multiple levels
Space amp Low-ish Higher until compaction

Bloom filter example: m bits, k hashes. Query "key X?" → if any bit is 0 → definitely absent (skip disk); if all 1 → maybe present. 10 bits/key, 7 hashes ≈ 1% false positives.

16.2 Modeling example – normalization vs denormalization

Normalized:

users(id, name)   orders(id, user_id FK, total)   order_items(order_id, product_id, qty, price)

16.4 Replication in practice

Leader-follower:
 App --writes--> [Leader] --WAL stream--> [Follower1]  <-- reads (may be stale)
                                    \---> [Follower2]
  • Replica lag problem: user posts a comment (to leader) then refreshes (reads follower) → comment missing. Fixes: read-your-writes (route that user to leader for N seconds, or session token with LSN), monotonic reads (stick user to one replica).
  • Failover risk: async replica promoted; last few transactions lost (RPO>0). Old leader returns → must be fenced/demoted to avoid split-brain.
  • Multi-leader: two regions accept writes → conflict e.g. both edit title. Resolve: last-write-wins (loses data), merge via CRDT, or app-level.
  • Leaderless quorum: N=3, W=2, R=2 ⇒ R+W>N so reads overlap latest write.
write x=5 -> nodes A,B ack (W=2), C missed
read -> asks A,C (R=2): A has x=5, C has old -> return newest (by version/vector clock) + read repair C

16.5 Sharding example

Users 1 B rows, 1 KB each = 1 TB; 20 K writes/s too many for one node → shard.

shard = hash(user_id) % N   (simple, but changing N moves almost all keys)
consistent hashing ring:    hash ring with vnodes; add node -> only ~1/N keys move

 ring:  0 ---A---B---C---A---B---C--- 2^32   (vnodes spread load; key goes to next node clockwise)
  • Cross-shard query ("all orders over $100") = scatter-gather. Cross-shard transaction = saga/2PC. Choose shard key to keep related data together (tenant_id, user_id).
  • Hot shard example: celebrity user → key salting (userId#0..9) spreads writes; reads aggregate.
  • Range sharding hotspot: timestamp key means all current writes hit last range; prefix with hash bucket.

// simple token bucket
class TokenBucket {
  private final long cap, refillPerSec; private double tokens; private long last = System.nanoTime();
  TokenBucket(long cap,long r){this.cap=cap;this.refillPerSec=r;this.tokens=cap;}
  synchronized boolean tryAcquire(){
    long now=System.nanoTime(); tokens=Math.min(cap,tokens+(now-last)/1e9*refillPerSec); last=now;
    if(tokens>=1){tokens--;return true;} return false; }
}

App -> Browser: redirect to IdP /authorize?client_id&code_challenge&scope=openid
User authenticates at IdP, consents
IdP -> Browser -> App: redirect with ?code=abc
App -> IdP /token: code + code_verifier  -> {access_token, id_token (OIDC), refresh_token}
App -> API: Authorization: Bearer <access_token>

OAuth = delegated authorization; OIDC adds the identity layer (id_token).

JWT anatomy & pitfalls: header.payload.signature (base64url). Validate signature, exp, aud, iss; reject alg:none; keep short-lived (5–15 min); revocation requires deny-list or short TTL + refresh rotation. Don't store secrets in payload (it's only encoded).

Password storage: argon2id(password, unique salt) – slow on purpose. Never SHA-256 alone; never reversible encryption.

18.3 Observability – examples

Three pillars wired together

Request -> trace_id=abc123 (header traceparent)
 logs   : {"ts":..,"level":"ERROR","trace_id":"abc123","svc":"payments","msg":"timeout","order":9}
 metrics: http_request_duration_seconds_bucket{route="/pay",status="500"}
 traces : gateway(5ms) -> orders(40ms) -> payments(900ms!) -> bank-api(880ms)   => culprit found

RED dashboard: Rate (req/s), Errors (% 5xx), Duration (p50/p95/p99). USE: Utilization, Saturation, Errors for resources (CPU, queue depth). Percentile example: 99 requests at 100 ms and 1 at 10 s → average 199 ms hides the 10 s; p99 = 100 ms, p99.9 reveals it. Use histograms, not averages. Cardinality trap: metric label user_id with 10 M users = 10 M time series → TSDB melts. Put high-cardinality detail in logs/traces, not metric labels. Alert design: page on user-visible symptoms (SLO burn), not on "CPU 80%". Incident flow: detect → declare severity → incident commander → mitigate (rollback first, root-cause later) → communicate → blameless postmortem with action items. Health checks: liveness (is process stuck? restart), readiness (can I serve? remove from LB during warm-up or dependency outage), startup probe for slow boots. Don't make liveness depend on the database – you'll restart-loop during a DB outage.
